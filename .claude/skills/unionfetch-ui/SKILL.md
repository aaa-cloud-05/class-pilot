# UnionFetch の UI を作る

Google Classroom と WebClass の課題を集約する学生向け PWA。**モバイル優先、PC も作る。**
背景と経緯は `docs/ui-playbook.md`、画面仕様は `docs/ui-redesign.md`、
本番への移行状況は `docs/ui-v5-migration.md`。基準の実装は `src/app/mock-v5/`。

---

## 0. 最初にやること

1. **`AGENTS.md` の指示に従う。** この Next.js は学習データと違う。
   書く前に `node_modules/next/dist/docs/` の該当ガイドを読む。
2. 変更対象が**本番の画面か、モックか**を確認する。本番の見た目を変えるなら、
   まず `docs/ui-v5-migration.md` の対応表で「その画面が移行済みか」を見る。
3. 迷ったら `src/app/mock-v5/` の同じ部品を読む。**v5 が正**。v1〜v4 は参考にしない。

---

## 1. やってはいけないこと（優先度順）

1. **本番のトークン（`:root`）をモック作業で触らない。** モックのトークンは `[data-uiN]` に閉じる。
2. **`npx shadcn add` を無検査で流さない。** 実行前に `git status` をきれいにし、
   実行後に `git diff` を全部読む。過去に `src/lib/utils.ts` と `globals.css` を壊された。
3. **ポータルを使う部品（Dialog/Drawer/DropdownMenu/Tooltip/Sonner）をスコープ付きトークンの中で使わない。**
   `document.body` 直下に出るのでトークンが効かない。自前の `Sheet` を使う。
4. **読ませたい情報に `initial: { opacity: 0 }` を付けない。** 動かすなら `y` のずれだけ。
   装飾（棒グラフ・カード・バッジ）は opacity 0 から出してよい。
5. **`sticky` を高さの小さい親の中に置かない。** スクロールする範囲を包む要素の直下に出す。
6. **グラフの目盛りを勝手に決めない。** このプロジェクトは §3 の表に従う（週の棒グラフは動的目盛り）。
7. **1行の中で色を2か所に置かない。** 左端＝押す場所（無彩色）、右端＝状況（色）。
8. **文言を性格にしない。** 「余裕派」ではなく「早め（24時間前に1回）」。
9. **「完了しています」「次にやる」のようなナレーションを足さない。** 数字と状態だけ出す。
10. **個人の Gmail アドレスを画面・コード・docs に書かない。** 公開連絡先は `support@unionfetch.com`。

## 2. 色 — 状態は1枚の表から導く

**色の意味を各コンポーネントで独自に決めない。** 1か所（`status-bar.tsx` 相当）に表を置き、
リスト・カレンダー・グラフ・ヘルプの説明を**すべてそこから引く**。
v5 では、ここを分散させたせいで「提出済み」が
リストでは青、カレンダーでは灰、ヘルプの説明では緑、と3通りになった。

| 意味 | トークン | 使う場所 |
|---|---|---|
| 締切を過ぎた未提出 | `--destructive` | グラフ / バー / ドット / 残り時間の文字 |
| 24時間以内が締切 | `--ui-warn-fill`（ライト・ダーク同値） | 同上 |
| まだ先の未提出 | `--primary` 75% | 同上 |
| 不明 | `--muted-foreground` 45% | 同上（リストは `?` の丸） |
| 提出済み | `--muted-foreground` 25% | 同上（リストは取り消し線） |

原則:

- **色は「塊で見る場所」に集約する。** 棒グラフ・進捗バー・カレンダーのドット。
- **1件ずつ読むリストは文字で足りる。**「あと3時間」「2日超過」。
- アクセント（青）は**操作**にも使うので、状態色として使うときは
  「押せるものに見えないか」を必ず確認する。
- 新しい状態を足したくなったら、まず**既存の5つに畳めないか**を考える。

## 3. 溢れたときの挙動 — 部品を書く前に決める

| 場所 | ルール |
|---|---|
| 週の棒グラフ | **その週でいちばん多い日が満杯**（動的目盛り・最大66px・最低8px）。件数の少ない週が寂しくならないことを優先し、週をまたいだ比較はカレンダーに任せる |
| ミニカレンダー・スマホの月/週 | **ドット4つまで**、5つ以上は末尾に `+` |
| PC の月カレンダー | **課題名2件まで**、3件以上は青字で「すべて見る」→ その日を選択 |
| PC の週カレンダー（縦に長い列） | 全部出す |
| リスト | 期間で区切る（月・週）。無限に伸ばさない |

新しい密なビューを作るときは、この表に**行を足してから**実装する。

## 4. 寸法とモーションの基準値

```
リストの行   min-h-60px / 本文 15px・行間1.5 / 補助 13px
見出し       セクション 14px semibold / 画面 22px bold（PC 24px）
丸チェック    22px（詳細 26px）、タップ領域は必ず 44px
ボタン       32 / 36 / 40px（sm / md / lg）、文字 14px weight 500
角丸         コントロール 6px、カードは --radius-card
影           使わない。0 0 0 1px var(--ui-line) の線で区切る
棒グラフ      最大 66px / 幅 28px / 間隔 6px
進捗バー      高さ 6px
```

```ts
// 数値は _components/motion.tsx に集約し、各所で書かない
SPRING      = { type: "spring", stiffness: 330, damping: 33, mass: 0.95 }
SPRING_SOFT = { type: "spring", stiffness: 180, damping: 26 }
EASE_OUT    = { duration: 0.65, ease: [0.16, 1, 0.3, 1] }
// CountUp 1.0s / 進捗バー 0.75s・段差 0.09s / 棒グラフ 段差 0.055s
```

`<MotionConfig reducedMotion="user">` を必ず入れる。`motion` からインポートする（`framer-motion` は使わない）。
込み入ったことをする前に `motion` スキル / Motion MCP でドキュメントを引く。

## 5. 画面の骨格

```
モバイル: 上に MobileHeader（home / title / back の3種）
          下に BottomNav 3タブ（ホーム・カレンダー・設定）＋ 中央 FAB（追加）
          ホームのヘッダーに 同期ドット と 通知ベル（未読ドット）

PC:       左に固定サイドバー 240px（ホーム・カレンダー・通知・設定）
          設定の中はさらに 2ペイン（左に項目一覧、右に中身）
          ホーム・カレンダーは 右カラム（選択した課題の詳細 or ミニカレンダー）
```

- 設定のサブページは `MobileHeader variant="back"` ＋ `PageBody desktopTitle` で揃える。
  ヘルプ記事も**同じ骨格**にする（左の設定一覧を出したまま開く）。
- 期間の単位は **ホーム＝週 / カレンダー＝月 / すべて＝月の中の週**。増やさない。
- タブ名と中身を一致させる。名前が嘘をつくなら、中身ではなく名前を変える。

## 6. 日本語の文言

- **起きることを書く。** 「早め（24時間前に1回）」「1日6件で満杯」。
- **主語を増やさない。**「あと 7 件」「提出済み 2 / 9」「期限切れ 1」。
- **ナレーションを足さない。**「完了しています」「次にやる」は消した。
- 見出しは体言止め（「画面の見かた」「同期のしくみ」「安全性とよくある質問」）。
- 説明はアコーディオンの Q 形式（「点の色の意味」「課題が多い日の見え方」）で揃える。
- 数字には `tabular-nums`。

---

## 7. 新しい画面・機能を足すときの手順

1. `docs/ui-redesign.md` の**機能対応表に行を足す**。既存機能を潰していないか確認する。
2. **溢れたときの挙動**を §3 の表に足す。
3. **状態の色**が要るなら §2 の表から引く。新しい色は増やさない。
4. `src/app/mock-v5/` に実装する（本番移行が済んでいる画面なら本番に直接）。
5. `npx eslint src/app/mock-v5` → `npx tsc --noEmit` → `npx next build` を通す。
6. **DOM で検証する**（§8）。スクリーンショットは補助。
7. 見た目の良し悪しは**ユーザーが判断する**。実装して、数字で確かめられることだけ確かめて渡す。

## 8. 検証のしかた

スクリーンショットは当てにならない。ブラウザのペインが裏に回ると `requestAnimationFrame` が止まり、
入場アニメーションが `opacity: 0` のまま固まって「真っ白」に写る。
`document.hidden` を疑う前に、**数えて測る**。

```js
// 溢れのルールが効いているか
[...document.querySelectorAll("div")]
  .filter(d => d.className.includes("min-h-[116px]"))
  .map(c => ({ chips: c.querySelectorAll("button").length - 1, more: c.textContent.includes("すべて見る") }))

// sticky が本当に貼り付いているか（複数のスクロール位置で）
for (const y of [0, 600, 1400]) { window.scrollTo(0, y); await new Promise(r => setTimeout(r, 250))
  console.log(y, el.getBoundingClientRect().top) }

// 色が意図どおりか（トークンは [data-uiN] スコープなので :root からは読めない）
getComputedStyle(el).color   // rgb(227, 177, 105) === #e3b169
```

ダミーデータには必ず「**課題が6件重なる日**」を入れておく（`_lib/data.ts` の `inDays` 群）。
極端な状態が既定で見えていないと、そのケースは設計されない。

## 9. プロジェクトの制約（UI 作業でも効くもの）

- **PR は作るが、マージはユーザーがする。** 作業は feature ブランチ → PR。
- **複雑すぎる実装を避ける。** ユーザーの明示的な好み。
- DB スキーマ変更は `prisma db push`。`migrate dev` は使わない。
- Windows で `prisma generate` が EPERM のときは dev サーバを止めてから。
- コミットメッセージ・PR 本文にメールアドレスを書かない。
