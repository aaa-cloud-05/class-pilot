# UI プレイブック — v1〜v5 で分かったこと

最終更新: 2026-09-22

`/mock` から `/mock-v5` まで5回作り直した過程で分かった、**このプロジェクトで UI を作るときのやり方**。
画面ごとの仕様は `docs/ui-redesign.md`、本番への移行計画は `docs/ui-v5-migration.md` にある。
ここには「どう進めるか」「何をやってはいけないか」だけを書く。

---

## 1. 進め方（これが一番効いた）

### 1.1 本番に触らずにモックを作る

```
src/app/mock-v5/
  layout.tsx          ← process.env.VERCEL_ENV === "production" なら notFound()
  ui-tokens.css       ← [data-ui5] { ... } にスコープを閉じたトークン
  _components/        ← モック専用の部品（_ 始まりなのでルートにならない）
  _lib/               ← ダミーデータと表示用ロジック
  (app)/…             ← 画面
```

守ったルール:

- **トークンは `[data-ui5]` の中だけに書く。** `:root` を触らない。`globals.css` から
  `@import "./mock-v5/ui-tokens.css"` するだけなので、本番の見た目は1pxも変わらない。
- **API・DB・hooks に一切触らない。** データは `_lib/data.ts` の `SEEDS` から「いま」を基準に組み立てる。
  いつ開いても「今日」が今日なので、日付まわりのバグがそのまま見える。
- **本番では 404。** ローカルと Vercel のプレビューでだけ見られる。
- 捨てるのが安いので、思い切った案を出せる。実際 v3 は丸ごと捨てた。

### 1.2 作り直したものを消さない

v1〜v5 は全部残してある。これが効いたのは、ユーザーが
**「v2 と v3 の中間がマジでベスト」**と言えたから。片方しか残っていなければ、この判断はできなかった。

- 新しい版は前の版の**コピーから始める**（v5 は v2 のコピー）
- 版ごとにトークンのスコープを分ける（`[data-ui]` `[data-ui2]` … `[data-ui5]`）
- 「どれを採用したか」を版ごとに `docs/ui-redesign.md` に残す

### 1.3 サイズと速度は「実測」で決める

推測で `text-sm` や `p-4` を選ばない。**実在の SaaS を開いて computed style を読む。**

```js
// ブラウザのツールで、参考にしたいサイトを開いて実行する
const b = document.querySelector("button")
const s = getComputedStyle(b)
;({ h: b.offsetHeight, font: s.fontSize, weight: s.fontWeight, r: s.borderRadius, t: s.transition })
```

Vercel Geist から取った実測値（v5 の基準になっている）:

| | 値 |
|---|---|
| ボタン高さ | 32 / 36 / 40px（sm / md / lg） |
| ボタン文字 | 14px / weight 500 |
| 角丸 | 6px（コントロール） |
| トランジション | 150ms `cubic-bezier(.4,0,.2,1)` |
| グレー | `#ebebeb`（線） `#fafafa`（面） `#171717`（文字） |
| 青 / 赤 | `hsl(212 100% 48%)` / `#da2f35` |
| 影 | 使わない。`0 0 0 1px` の線で面を区切る |

この物差しがあったから「v2 は全部が1サイズ大きい」「v3 は小さすぎて目をしかめる」と**言語化できた**。
感想ではなく数字で比べられる状態を先に作る。

### 1.4 機能対応表を先に作る

タブ構成を変えるとき、ユーザーの最初の条件は「**今ある機能が1つも減らないこと**」だった。
そこで、現行の全機能（43個）を洗い出して、v5 のどこに行くかの表を `docs/ui-redesign.md` に作った。
画面を1つ差し替えるたびにこの表にチェックを付ける。**これをやらないと必ず何か落ちる。**

### 1.5 検証は DOM で、見た目はユーザーが

- **スクショは当てにならない。** ブラウザのペインが裏に回ると `requestAnimationFrame` が止まり、
  `initial: { opacity: 0 }` のモーションがそのまま止まって「真っ白」に写る。何度も騙された。
- 代わりに `javascript_tool` で**数えて測る**。

```js
// 例：月セルのチップが2件＋「すべて見る」になっているか
[...document.querySelectorAll("div")]
  .filter(d => d.className.includes("min-h-[116px]"))
  .map(c => ({ chips: c.querySelectorAll("button").length - 1, more: c.textContent.includes("すべて見る") }))

// 例：sticky が本当に貼り付いているか（親の箱に閉じ込められていないか）
window.scrollTo(0, 1400)
el.getBoundingClientRect().top   // 期待値に張り付いていなければバグ
```

- **見た目の良し悪しはユーザーが判断する。** Claude は実装と、数字で確かめられることの検証だけ。

## 2. アンチパターン（実際にやらかしたもの）

### 2.1 LP 向けのデザイン言語をアプリ画面に持ち込む

最初の `DESIGN.md` を Vercel 基調で書いた結果、
「ミニマルすぎて素っ気ない」「ボタンが小さい」「リストが窮屈」になった。

- **LP は読ませる画面**。余白が主役で、タップ対象が少ない
- **アプリは操作させる画面**。1行が押せることが分かり、44px の指が入る必要がある

tasteskill 系（`design-taste-frontend` `minimalist-ui` `high-end-visual-design`）は
LP が守備範囲。アプリの一覧画面には**配色と余白の作法だけ**を借りて、
サイズとタップ領域は `ui-ux-pro-max` 側のルールで決める。

### 2.2 作り込みすぎ（v3）と、その反動（v2）

| | 症状 |
|---|---|
| v2 | 全部が1サイズ大きい。スクロールが増え、一覧性が落ちる |
| v3 | 細い罫線を増やし、文字を小さくし、情報を詰めた。**目をしかめる** |
| v5 | v2 の骨格に v3 の温度感だけを足す |

課題アプリは**パッと見えることが命**。凝った区切り線より、行の高さと文字サイズが効く。

### 2.3 shadcn CLI を既存プロジェクトに素で流す

`npx shadcn@latest add …` が本番コードを壊した。

- `src/lib/utils.ts` が `export { cn } from "cn"` に置換された（`cn` という別パッケージを勝手に入れた）
- `globals.css` の `--font-sans: var(--font-sans)` が自己参照になった
- `--radius` が書き換わり、`@import` が重複した

**対策:** CLI を走らせる前に `git status` をきれいにし、走らせた直後に必ず `git diff` を全部読む。
生成物をそのまま信じない。

### 2.4 ポータルを使う部品をスコープ付きトークンの中で使う

shadcn の Dialog / Drawer / DropdownMenu / Tooltip / Sonner は `document.body` 直下に描画される。
`[data-ui5]` の**外**に出るのでトークンが効かず、色が全部壊れる。

モックでは自前の `Sheet` / `Segmented` を書いた。本番に移すときも、
ポータルを使うなら**トークンは `:root` に置く**か、ポータル先にも属性を付ける。

### 2.5 色を「状態」と「操作」の両方に使う

1行の中に色が2か所（左の丸と右の時間）あると、**どちらを見れば優先順位が分かるのか**が曖昧になる。

決めたルール:

> **左端＝押す場所（無彩色）／右端＝状況（色を持つ）**
> 色は「塊で見る場所」（棒グラフ・進捗バー・カレンダーのドット）に集約する。
> 1件ずつ読むリストは、文字（「あと3時間」「2日超過」）で足りる。

### 2.6 情報そのものに `initial: { opacity: 0 }` を使う

カレンダーのチップに入場アニメーションを付けたら、JS が走るまで**中身が存在しない**画面になった。
装飾（棒グラフ・カード）は 0 から出してよいが、
**読ませたい情報は opacity 1 から始めて、動きは `y` のずれだけ**にする。

### 2.7 `sticky` を小さい親の中に置く

```tsx
<div>                          {/* 高さ 70px */}
  <div className="sticky top-…">月ナビ</div>   {/* ← 70px 分しか貼り付かない */}
  <p>件数</p>
</div>
```

sticky は**親の箱の中でしか止まらない**。スクロールする範囲を包む要素の直下に出す。
実際この形で1回バグを作り、スクロール3地点の `getBoundingClientRect().top` を測って直した。

### 2.8 目盛りは「比べられること」と「寂しくないこと」のどちらを取るか

棒グラフの高さを `peak = Math.max(...その週の件数)` で正規化すると、
**週をまたぐと目盛りが変わり、忙しさを比べられない**。
一方で固定目盛り（例：1日6件で満杯）にすると、件数の少ない週は棒がほとんど伸びず寂しくなる。

**このプロジェクトの決定: 動的（その週でいちばん多い日が満杯）を採る。**
毎日開く画面なので「今週の中でどの日が重いか」が読めることを優先し、
週をまたいだ比較はカレンダーと「すべて」タブに任せる。

どちらを採るにせよ、**実装前に決めて表に残す**（§3.6）。あとから変えると説明文も直すことになる
（実際、ヘルプの「1日6件でいちばん高くなります」を書き直した）。

### 2.9 ダミーデータが「ちょうどよすぎる」

1日に最大2件しかないデータで作っていたので、
**溢れたときの挙動を決め忘れていた**（ドットが3つ目から出ない、チップが重なる、棒が潰れる）。

→ モックデータには必ず「**課題が6件重なる日**」を入れる（`_lib/data.ts` の `inDays: 3` の群）。
極端な状態が既定で見えていないと、そのケースは設計されない。

### 2.10 文言を「人柄」にする

通知プリセットを `余裕派 / 標準 / ギリギリ派` にしたら「ダサい」と言われた。
設定の選択肢は**性格診断ではなく、起きることを書く**。

→ `早め（24時間前に1回）/ 標準（24時間前と3時間前）/ 直前（3時間前と1時間前）`

同じ理由で「完了しています」「次にやる」のようなナレーションも削った。
数字と状態だけ出して、意味づけはユーザーに任せる。

## 3. 原則（抽象論）

### 3.1 単位を揃える

| 画面 | 単位 |
|---|---|
| ホーム | **週**（今週の状況 + 直近のリスト） |
| カレンダー | **月**（週にも切り替わる） |
| すべて | **月の中を週で読む** |

同じアプリの中で「期間の粒度」が3つも4つもあると、頭の中の地図が作れない。
週と月だけにして、行き来のしかたを揃える。

### 3.2 タブ名と中身を一致させる

「すべて」なのに来週以降が出ない、は最悪。名前が嘘をつくと、ユーザーは探すのをやめる。
中身を変えられないなら、**名前のほうを変える**。

### 3.3 有限にする

無限に伸びるリストは開く理由を奪う。月で区切る、週の塊にする、空の週は出さない。
「この画面は読み切れる」と思えることが、毎日開く理由になる。

### 3.4 完了を見せる

未提出しか出ないアプリは「管理されている感じ」しか残らない。
今日・明日・今週のような**近い範囲では提出済みも出す**（灰色＋取り消し線で沈める）。
進捗バーも「残り」ではなく「今週の全構成」を色で埋める。

### 3.5 不確実さを隠さない。ただし片づける導線を必ず作る

WebClass は提出状況が取れないことがある（＝このプロダクトの本質）。
「不明」を灰色で黙らせるのではなく、`?` の形で見せる。
そのうえで**まとめて確認する入口**（ホームの1行 → 不明だけのシート）を必ず置く。
見せるだけで解決手段がないのは、ただのノイズ。

### 3.6 溢れたときの挙動を、実装前に数字で決める

| 場所 | ルール |
|---|---|
| ホームの棒グラフ | **その週でいちばん多い日が満杯**（動的目盛り・最大66px、最低8px） |
| ミニカレンダー・スマホのカレンダー | ドット4つまで、5つ以上は末尾に `+` |
| PC の月カレンダー | 課題名2件まで、3件以上は青字で「すべて見る」→ その日を選択 |

「多いときどうなるか」は、後から考えると必ず破綻する。**部品を書く前に表にする。**

### 3.7 モーションは「順番」を伝えるためだけに使う

- 基準値は1か所（`_components/motion.tsx`）に置き、各所でバネの数値を書かない
- `MotionConfig reducedMotion="user"` を必ず付ける
- 数字はカウントアップ、棒は下から伸びる、リストは上から順に出る、くらいでよい
- 「ちょっと長め」がこのアプリの好み: `EASE_OUT 0.65s cubic-bezier(.16,1,.3,1)`、段差 0.05〜0.09s

## 4. v5 の確定値（そのまま本番に持っていく）

### 4.1 色

| 意味 | 色 | 使う場所 |
|---|---|---|
| 締切を過ぎた未提出 | `--destructive` 赤 | 棒グラフ・進捗バー・ドット・残り時間の文字 |
| 24時間以内が締切 | `--ui-warn-fill` `#e3b169` | 同上（**ライト/ダークで同値**） |
| まだ先の未提出 | `--primary` 75% 青 | 棒グラフ・進捗バー・ドット |
| 不明 | `--muted-foreground` 45% 灰 | 同上。リストでは `?` の丸 |
| 提出済み | `--muted-foreground` 25% 灰 | 同上。リストでは取り消し線 |

> ⚠️ 現行アプリは「提出済み＝緑」。この1点は本番移行で必ず決め直す（`docs/ui-v5-migration.md` 参照）。

### 4.2 寸法

| | 値 |
|---|---|
| リストの行 | `min-h-[60px]`、本文 15px/1.5、補助 13px |
| 見出し | 14px semibold（セクション）、22px bold（画面） |
| 丸チェック | 22px（詳細は26px）、タップ領域は 44px |
| カード | 影なし。`0 0 0 1px var(--ui-line)` |
| 棒グラフ | 最大 66px、幅 28px、間隔 6px |
| 進捗バー | 高さ 6px、角丸フル |

### 4.3 モーション

```ts
export const SPRING      = { type: "spring", stiffness: 330, damping: 33, mass: 0.95 }
export const SPRING_SOFT = { type: "spring", stiffness: 180, damping: 26 }
export const EASE_OUT    = { duration: 0.65, ease: [0.16, 1, 0.3, 1] }
// CountUp 1.0s / 進捗バー 0.75s・段差 0.09s / 棒グラフ 段差 0.055s
```

## 5. スキルの使い分け

| 場面 | 使うもの |
|---|---|
| 配色・書体の候補、UX ルール（タップ領域・ナビ・フォーム・コントラスト） | `ui-ux-pro-max` |
| 既存画面の「AI っぽさ」監査 | `redesign-existing-projects` |
| モノクロ方向の味付け | `minimalist-ui` |
| ログイン画面・将来のトップページ | `design-taste-frontend` |
| アニメーション | `motion`（公式スキル）＋ Motion MCP |
| **このリポジトリで画面を作る・直す** | **`.claude/skills/unionfetch-ui`** |

採用したルール: アクセント色は1つ・角丸の体系は1つ・装飾だけの色付きドットを使わない・
意味のないアニメーションを入れない・`prefers-reduced-motion` 対応・ライト/ダーク両方を最初から作る。

採用しないルール: lucide 禁止（依存済みなので継続）、LP 用のヒーロー/ベント規則。
